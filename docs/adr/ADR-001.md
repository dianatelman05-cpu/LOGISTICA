# ADR-001 Выбор модели поставки проекта LOGISTICA

- Статус: Принято
- Дата: 17 сентября 2026 года
- Проект: LOGISTICA
- Ответственный: команда проекта

## Контекст

LOGISTICA — клиент-серверная информационная система для управления работой логистической компании.

Система включает следующие модули:

- регистрацию и авторизацию пользователей;
- клиентов и заказы;
- водителей и транспорт;
- склады и маршруты;
- доставки и назначение водителей;
- историю изменения статусов;
- журналирование и отчёты.

Требования к интерфейсу и отдельным функциям могут изменяться после демонстрации проекта. При этом изменения базы данных и взаимосвязанных модулей должны контролироваться.

Необходимо выбрать модель поставки, которая позволит регулярно показывать работающий результат, получать обратную связь и постепенно развивать систему.

## Рассмотренные варианты

### Вариант 1 Каскадная модель

Преимущества:

- понятная последовательность этапов;
- подробная документация;
- простая итоговая приёмка.

Недостатки:

- работающий результат появляется поздно;
- изменения требований требуют больших затрат;
- интеграционные ошибки могут обнаружиться только в конце.

Решение: вариант отклонён.

### Вариант 2 Scrum с инкрементальной поставкой

Преимущества:

- разработка короткими спринтами;
- регулярная демонстрация результата;
- возможность изменять приоритеты;
- раннее обнаружение ошибок;
- постепенное добавление модулей.

Недостатки:

- требуется регулярно обновлять backlog;
- необходимо контролировать статусы задач;
- итоговый объём может уточняться во время разработки.

Решение: вариант принят.

### Вариант 3 Kanban

Преимущества:

- наглядное движение задач;
- ограничение незавершённой работы;
- непрерывный рабочий процесс.

Недостатки:

- отсутствует фиксированный ритм спринтов;
- сложнее привязать результат к учебным контрольным точкам.

Решение: отклонён как основная модель. Элементы Kanban используются на доске GitHub Projects.

### Вариант 4 Big Bang

Преимущества:

- минимум организационных процедур;
- единая итоговая поставка.

Недостатки:

- высокий риск интеграционных ошибок;
- отсутствие ранней обратной связи;
- сложность исправления ошибок перед сдачей.

Решение: вариант отклонён.

## Решение

Для проекта LOGISTICA выбран Scrum с двухнедельными спринтами и инкрементальной поставкой.

Разработка выполняется следующими инкрементами:

1. Регистрация, авторизация и роли пользователей.
2. Клиенты и заказы.
3. Водители и транспорт.
4. Склады и маршруты.
5. Доставки и назначение ресурсов.
6. История, журналирование и отчёты.

Работа проекта управляется через Issues и GitHub Projects. Каждая задача должна иметь тип, приоритет, модуль, статус, исполнителя и критерии готовности.

## Последствия решения

### Положительные последствия

- работающий результат появляется на ранних этапах;
- преподаватель может видеть ход выполнения проекта;
- ошибки обнаруживаются после каждого спринта;
- приоритеты задач можно изменять;
- система развивается отдельными модулями.

### Отрицательные последствия

- необходимо регулярно обновлять доску;
- требуется поддерживать актуальность backlog;
- часть требований может изменяться;
- необходимо тратить время на проверку результатов спринта.

### Риски

Изменение структуры базы данных может повлиять на уже реализованные модули.

Для снижения риска изменения базы данных версионируются, код проверяется перед объединением, а основные функции тестируются.

## Правила пересмотра решения

Решение необходимо пересмотреть, если:

- длительность спринта не позволяет получать готовый результат;
- количество незавершённых задач постоянно растёт;
- меняются основные требования проекта;
- выбранная модель мешает выполнению учебных контрольных точек.
